# BN2 / BN3 / BN4 - causes read from Tj's tablet report (2026-11-09 03:02 UTC, v0.8.12) and the fixes (design)

Sources: `research/tablet/2026-11-09/` (redacted report), `research/PATCH_MAP_BN2_BN3_2026-11-09.md` (code map), `TjAccessibilityService.java` (TAS) read at the lines named below.
Evidence limit: causes below are READ from the log + code, not filmed. Every fix therefore also adds a log line so the next report proves it.

## BN2 - first side-key press on the custom home showed the Screenshot entry; a tall card flashed

Log timeline (device clock): Enter tap 57.520 -> window `PATCH window created` 58.232 (home flavour, not restable) -> USER_PRESENT 58.435 -> `HOMEPATCH patch built, fresh=true` 59.310 (1.08 s after the window) -> side key ~59.65: `PATCH fast skip: the patch is not resting` 59.768 -> scan found the menu 59.960, `lag=306 ms`, short card `CARD area=[485,339][596,547] lockPatch=true` and the patch hidden = stock Screenshot entry visible. Home key 07.9: `menu closed` 07.869, `PATCH removed` 07.880, 143 ms later `menuOpen=true found=true` 08.012 and `CARD area=[485,339][596,642] lockPatch=false` (the TALL card, lived 250 ms: `hold: no menu text found` 08.170, `menu closed` 08.265).

1. **Why the patch was not restable at 59.65 although the composite was fresh at 59.31:** `homeForeignWindow` (TAS 667-688) counts ANY named window event that is not ours and not `ActionsDialog` as foreign and keeps the patch away for `HOME_FOREIGN_AWAY_MS` = 2500 ms. The keyguard's own SystemUI window (class `android.widget.FrameLayout`, the status-bar window) announces itself while it goes away, so every plain unlock started the 2.5 s guard (report: "foreign windows seen 8 (com.android.systemui android.widget.FrameLayout; the last 35 s ago)" = the unlock). Guard until ~60.8, press at 59.65 -> `patchRestable` false -> `fastDecline` (TAS 155) -> card path.
   FIX: a SystemUI window event within `UNLOCK_GRACE_MS` (3 s) of the keyguard being seen up does NOT start the 2.5 s guard: the patch goes away at once (alpha 0, cheap) and a recheck 400 ms later decides by the Launcher's window focus (the shade takes the focus, the keyguard's exit does not). Pure rule in `HomePatchRules.foreignTreatment`, pinned by JVM tests.
2. **The slow path answers 300+ ms late** (SystemUI + the Launcher share the service's main thread right after an unlock). Not fixed by itself: the fast path (patch ready) does not need it. Presses within ~1 s of an unlock (before the first composite) still use the card; measured in the new emulator step HP14.
3. **The tall card flash:** after a close the stock dialog's window stays in the window list, with its text, for its ~250 ms fade-out. `evaluateScan` (TAS 2989-2995) shows the cached card at once when `dialogUp` and nothing is open, and has no memory of a close. FIX: `menuClosedAtMs` (set when the open look ends, `patchShow(false)` with `patchOpenFlag`), and `evaluateScan` ignores a "dialog is up" for `PowerMenuRule.DYING_DIALOG_MS` (450) after it unless the dialog announced itself again (`fastMenuOpen` resets it: a NEW window event of class `ActionsDialog` is a real opening). Pure rule `PowerMenuRule.dyingDialog`.

## BN4 - white box on the lock screen after the shade slides back up (pencil cover)

`findPencil` (TAS 2162-2178) follows ONE known node. When SystemUI hides the pencil (the QS collapses: alpha 0 or `INVISIBLE`; an INVISIBLE view cannot be refreshed: `AccessibilityInteractionController.isShown`), the node is dropped, and unless a FULL tree search is allowed (spaced 200 ms for content changes, `EventNoise.minPencilSearchGapMs`) `penSearched` stays false and `updatePencil` (TAS 2144-2151) does NOT hide the opaque white cover (`Color.WHITE`, TAS 2234). The cover stays where the pencil was until the next allowed search (200 ms + search time, up to ~500 ms on the tablet): on a white panel invisible, on the lock screen a white box once the panel has gone.
FIX: losing the followed node (refresh failed, invisible, bad bounds) hides the cover AT ONCE (`hidePencil`, cheap), the node is dropped and the full search is allowed promptly (the 200 ms gap is waived once) to re-show it if the pencil is really still there; a 150 ms watchdog re-checks while the cover is up (events stop when the shade stops moving); a lock-log line records every loss-hide with its age.

## BN3 - lock patch flashes while the PIN pad is pulled up

The finger-down hide (`onOutsideTouch`, TAS 3689) is the earliest signal and runs (report lines 21:58:49.682 / 52.695: pad sign 104 / 119 ms after the finger). No flash is visible in the 40-line log, so the cause is NOT proven. Candidate returns (map section 6.4): `touchBack` +920 ms after the DOWN shows the patch again with no check of the pad; a pull whose pad sign comes later; the frame latency of `setAlpha(0)` (2-3 frames) against the first frames of the stock bouncer scrim.
FIX (cheap, no new risk): (a) `touchBack` runs the same fresh pad look as `padBack` before it shows the patch (a pad that is up or coming keeps it away); (b) every return and every late hide writes a rate-limited lock-log line `PATCH visible again (touchBack|padBack|restRecheck|...) N ms after the finger / pad sign` so the next tablet report names the path that flashed; (c) `TOUCH_AWAY_MS` 900 -> 1500 (an away patch costs nothing: the dialog's own event brings it back, see the `menu opened while the patch was away` line).
Not done: predicting the pull (no earlier signal than the finger's DOWN exists).
