## What a good finding is
Concrete: file:line (current head), what runs, how often, what it costs (CPU ms / allocation / RAM bytes / wakeups / battery), and an evidence tag: [V] verified by reading the
code, [I] reasoned from code + Android behaviour, [T] only Tj's tablet can show. Prefer: main-thread blocking (disk fsync via commit(), binder calls, process spawns, sleeps),
work repeated per event / per draw / per frame / per key, allocation in onDraw / onMeasure / adapters / event handlers, unbounded or never-released memory (statics, caches,
threads, listeners, bitmaps), polling loops and timers that run while the screen is off or the app is idle, duplicated work (same query twice in one call chain), missing early-outs
(do the cheap check first), over-large bitmaps / wrong Bitmap.Config, receivers / observers registered but not needed, leaks (Activity / View held by a static or a thread).
Do NOT report style, naming, "could be Kotlin", test gaps, or anything with no measurable cost. Do not pad: 6 solid findings beat 20 weak ones; "nothing found in X" is a valid and useful answer.
