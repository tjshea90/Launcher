# CG1B-A11Y: what the accessibility service costs per event and per loop (read-only review, 2026-11-17)

Slice: `TjAccessibilityService.java` ("TAS", 5266 lines) and the helpers on its event paths (`EventNoise`, `LockShade`, `PencilRules`, `UnlockMethods`,
`Features`, `FailsafeKeys`, `ReturnMethods`), plus `app/src/main/res/xml/tj_accessibility.xml`. Nothing was built, run or changed; this file is the only write.
Not repeated: `PERF_AUDIT_2026-11-13.md` (CA1: U1 fixed, S1-S12, U2-U12), `PERF_REVIEW_2026-11-12*.md` (BY1), `CG1B_PROCESS_PERF_2026-11-17.md` (its M7 asks this report about the flags: section 8).
Evidence: VERIFIED = read in this repo (file:line); INFERRED = reasoned, or Android 10 behaviour recalled from AOSP (list to re-check in section 12); the repo holds no AOSP source for the accessibility manager.
Ids are `E1..E13` (E = event path) so they do not collide with CA1's S/U, BY1's A-D or the process review's W/M/N.

## 0. Verdict

1. Per event our own code is cheap. A delivered event costs about 5 us when it is another app's content change (85 % of deliveries) and a few hundred us for the rest; no
   per-event disk write, no per-event allocation worth naming, no per-event `LockLog` line, no `SimpleDateFormat` on an event path (VERIFIED, sections 4 and 7).
2. The cost is cross-process tree searches, run by SystemUI's UI thread while OUR main thread (shared with Launcher3 and with the delivery of the next event) waits:
   `getRoot` + id or text walks. They happen at the wrong moments: on the lock screen, around PIN entry and around window bursts. Tablet anchors (report 2026-11-10-2, before BY1 and CA1): 984 power-menu
   scans x 28 ms + 834 pencil searches x 33 ms = about 55 s of main-thread block in 121 min (0.8 %), max 563 and 1305 ms. That is a latency problem (Enter lag 224 / 359 ms), not a battery problem.
3. CA1 U1 removed the power-menu scan and the pencil search for a PIN KEY CLICK. What it left: per PIN key the lock-number code still confirms "pad is up" two or three times
   (leading edge + trailing 120 ms + any content change after the key) and the pencil still searches on every content change of SystemUI while the pad is up (E1), and a pad that is NOT up
   is checked with 11 tree walks (E2, = CA1 S4). U1's own design item (d) (handle `trackUnlockKey` first) was never applied (TAS:94 before TAS:96).
4. Worthwhile, in this order: **E5** counters (no behaviour change), **E4** `profileNote` still commits on the main thread, **E3** the "Screenshot" search runs even when "Power off" is absent,
   **E1** quiet PIN entry, **E2** a learned minimal pad probe. Everything else is marginal or "measure first". No flag of `tj_accessibility.xml` should change (section 8).
5. Battery: nothing here wakes the CPU with the screen off; the event path is level-triggered; the only repeating loops are bounded jobs and the pencil watch (section 6). Estimated total
   battery effect of every finding in this report: below 0.1 % of a day. The reason to do E1-E5 is lock-screen latency, not energy.

## 4. What one event does (VERIFIED, TAS:67-105, main thread)

```
68      evSeen++
69-72   NOTIFICATION_STATE_CHANGED: NotifSightings (package only), return
73      diagEvent: one flag test in release builds
74      window events: noteWindowEvent + fastMenuOpen (class-name test; opens the patch at the dialog's own event)
75      every event: fastMenuClose (lock flavour only: PIN-pad class sign -> pinPadCameUp, no scan; string tests on the class name)
76      WINDOW_STATE_CHANGED: lockShadeEvent (pane-title bit test, then a title compare)
77-81   homeForeignWindow (only with a home patch window), trackForeground (WINDOW_STATE only, package change only), AnimationSpeedup.tick (window events, <= 2/s), PickerGuard, RecentsFilter (string compares)
83      own package: return
84-88   noise (CONTENT_CHANGED of any package except SystemUI / "android"): evNoise++, return          <- 85 % of deliveries end here, about 5 us
89-91   quietBurst; window events set fullScanUntilMs = now + 300; coverOn = powerMode != off && coverWorld()   (keyguard answer memoised 250 ms)
93      overlayShown: leadingEdge first
94      scheduleLockUpdate / scheduleLayerRefresh / schedulePencil        <- the three that start tree walks
95-98   trackDirty (WINDOW_STATE only), trackUnlockKey (CLICK from SystemUI only), probe, guardStrayHome
99-104  !coverOn: return (Quickstep with an app in front ends here); else leadingEdge -> evaluate()
```

Scan triggers in `leadingEdge` (TAS:108-118 with `EventNoise.needsPowerMenuScan`, EventNoise:45-49): every WINDOW_STATE_CHANGED and WINDOWS_CHANGED starts a scan (returns true unconditionally),
a click only from SystemUI/"android" with the pad down, a content change only when a menu is known up or inside the 300 ms window after a window event. A started scan runs at once if 40 ms
passed since the last one, and ALWAYS arms the 80 ms trailing `debounced` scan (TAS:44-49, 117): one isolated window event costs two scans.

## 7. Disk writes, `LockLog`, garbage on event paths

- VERIFIED: no `commit()` and no file write on an event path in steady state. `Features.setString` commits, but the sites that run per scan (`cardKey` / `itemKey` at TAS:3680-3681) write an identical value, and
  AOSP's `SharedPreferences` skips the disk write when the in-memory value is equal (generation not bumped; INFERRED from memory, about 10-30 us). `patchStatus`, `calStatus`, `shotStatus`, `homeStatus` are
  `apply()` and only on change (S12 verified in place).
- Sync commits that remain on the lock / unlock cycle (not per event): `profileNote` (E4), `bump` (TAS:3088, stray-home count), the reset report (U7, known).
- `LockLog.add` on event paths: only `PAD shown/hidden` (transitions), `ENTER` (one per Enter), `DIRTY` (one per package per minute), `penLockLog` (transitions). The queue / append / `f.length()` stat cost sits on
  the log thread (process review N2: fine). The string for each is built on the main thread, 50-200 bytes, a few per unlock: nothing to gain.
- `Log.i` in release on event paths: `UNLOCKCLICK` per PIN key and `KEY` per Back or volume key (one concat + one logd write, 30-60 us); `PATCH fast open` per menu open. Debug-only lines are guarded by `debuggable()`.
- Garbage per delivered event: none beyond the framework's recycled event. Per scan and per pencil look: result lists, `Rect` objects, `Settings`-style strings (`cardKey()` builds `"power_card_rect_r" + rotation()`
  and `split(",")` allocates 5 objects on every `cachedCard()`), `toLowerCase` copies inside the TARGET process for every text search. All bounded by the scan rate; E3 removes the largest block.

## 10. The worthwhile ones in detail

**E5. Counters (do first).** In `perfLine` add, as plain longs on the main thread: scans by trigger class (SystemUI window event, app window event, WINDOWS_CHANGED, content inside the 300 ms window,
menu known up, `debounced`, `recheck`, `quietWork`) with count and total ms; pad checks split positive / negative and by trigger (click, content, window, `lockEval`, broadcast); pencil full searches split by
state (pad up, lock screen with `lockShadeOpen` false or true, unlocked home, QS open); main-thread stalls over 100 ms with the trigger that caused them. About 40 lines, no behaviour change. This is what
turns E1, E2, E6, E8 from estimates into decisions, and gives Tj's next report a before / after for the lock-screen work.

**E4. `profileNote`.** `Features.setString` -> `Features.setStringAsync` in TAS:1787. The three call sites are the handshake accept (inside `secretAccepted`, right after the Quickstep start), the lock pre-arm and the
lock; none is read back after a process kill (it is a report line, `PREARM_REPORT_KEY`). `apply()` updates the in-memory map at once, so every reader in the process sees it.

**E3. One text walk less per scan.** TAS:3646-3647:
`sc = (off != null && !off.isEmpty()) ? root.findAccessibilityNodeInfosByText("Screenshot") : null;` Same decision (`menuOpen` needs both), same semantics for the branch that follows. Halves the
text walks of a scan that finds nothing, which is almost all of them.

**E1. Quiet PIN entry.** Today per key (pad up, no cover): click -> `scheduleLockUpdate` (leading `updateLockNumber`, trailing `lockEval`), `scheduleLayerRefresh`, then CA1's U1 exclusions, then `trackDirty`,
then `trackUnlockKey`. Content changes after the key repeat the first and start a pencil search. Proposed pure rules in `EventNoise` (JVM-tested like U1's):
`pencilSearchOnEvent(type, pinPadUp, coverShown) = !(pinPadUp && !coverShown)` (drop the CLICK restriction: with the pad up no pencil can be visible);
`padConfirmOnEvent(type, fromSystemUi, pinPadUp) = !(type == CLICKED && fromSystemUi && pinPadUp)` (a key click cannot change whether the pad is up; window events, content changes, the broadcasts and `lockEval`
after them keep every trigger of the pad-HIDE detection, exactly CA1's argument for leaving content changes alone); and in `onAccessibilityEvent` run `trackUnlockKey(event)` first when
`type == CLICKED && lastBouncer`. Exposure when `lastBouncer` is stale-true: the pad check of the same event (TAS:94) refreshes the flag BEFORE `schedulePencil`, so a pencil search is skipped for at most one event.
Residual risk to film: a quick-settings pull right after a cancelled pad (`fl` / `b6`).

**E2. Learned minimal pad probe.** A negative answer is the expensive one (11 walks) and the common one on a lit lock screen. Keep a tiny state: the index of the signal that last returned a visible node
(`padProbeIdx`, -1 = none), the uptime of the last full check, and a flag "pad-class sign since the last check" (set by `fastMenuClose`, TAS:4513-4517). Probe order: if idx >= 0 and the last full check
is younger than 3 s and no sign is pending: that one signal only; otherwise the full list, which also re-learns idx. A lock-type change (PIN -> pattern) is caught by the class sign and by the 3 s refresh.
All state on the main thread (like `lastBouncer`); reset at SCREEN_OFF. Needs a pure class and tests; ship after E5 has shown the negative-check count and cost.

## 11. Ordering and thread-safety notes for the changes above

1. `UnlockMethods.onPad` clears the entered-key buffer (UnlockMethods:130-134) whenever the pad flips; `onKey` appends (164-174); `onEnter` reads it (177). Running `trackUnlockKey` BEFORE the pad scan of the same
   event is only safe when the pad is already known up (`lastBouncer` true: `onPad(true)` has run). With the pad unknown the first key of an entry could be recorded and then erased by the late `onPad(true)`, and a
   handshake (TAP_ERASE, ERASE2, ...) would silently not arm. Hence the `lastBouncer` condition in E1.
2. `lastBouncer` is written only in `updateLockNumber` (TAS:2970) and read on the main thread only (`fastDecline`, `fastMenuClose`, `leadingEdge`, `schedulePencil`). E1 adds a reader; E2's probe state follows the same rule.
3. `lockEvalPending` / `lastLockEvalMs` stay consistent when a click skips `scheduleLockUpdate`: nothing is posted and nothing is stamped.
4. E4: `apply()` hands the write to the writer thread after updating memory; `Features.p(c)` is one shared handle (Features.java), so readers on any thread see the new string.
5. E11 (if ever): `AccessibilityService.getWindows()`, `getRoot`, searches and `recycle` may be called from any thread; every result applied on the main thread needs a generation counter (the screen state
   changes while a 500 ms search runs) and at most one search in flight with one pending, like `lockEvalPending`.
6. `screenDarkNow` (E7) is volatile and false until the first SCREEN_OFF broadcast, so a restarted service behaves as before.
