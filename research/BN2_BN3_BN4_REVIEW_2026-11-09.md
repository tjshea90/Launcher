# /code-review high of the BN2 + BN3 + BN4 diff (v0.8.12..ckpt 768) - findings and what was done (2026-11-09)

Ten findings, all read against the code. Fixed = changed in the next commit; Accepted = deliberate, with the reason, so nobody re-derives it.

| # | Finding | Verdict |
| :- | :- | :- |
| 1 | The unlock-grace branch hid the patch but started NO guard for 400 ms: a `patchShow` in that time (layerRefresh, homeShowCheck, scan event) could paint the patch back over a real window. | **Fixed.** The guard now starts at once as before but is PROVISIONAL (`homeForeignApply(name, provisional)`); only the recheck can lift it (`HomePatchRules.recheck`). During the 400 ms nothing can show the patch. |
| 2 | The deferred verdict assumed the shade takes the Launcher's focus; an early return dropped the pending verdict; a stream of events postponed it; a volume panel (no focus) would be judged "keyguard". | **Fixed.** (a) Only SystemUI's plain `android.widget.FrameLayout` window (the status-bar window; the tablet's counter named exactly that) can be "the keyguard going away"; every SystemUI Dialog (volume panel, power menu) announces itself with its own class and keeps the immediate final guard (`isKeyguardWindow`). (b) An early return leaves the provisional guard to run out (2.5 s, as in v0.8.12): nothing is lost. (c) A final guard cancels the recheck and the recheck lifts only the guard it armed (`RECHECK_NOT_OURS`). (d) The focus premise is the one the existing `homeRestable()` already relies on (HP11). |
| 3 | Every lost pencil triggered a second whole-tree search 30 ms later even when this call had just searched and found nothing. | **Fixed.** `searchGapWaived(followed, fullSearchRan)`: only when no search ran in the call. |
| 4 | A transient `refresh()` failure now hides the cover at once (the real pencil shows until the retry finds it). | **Accepted.** Tj's report is the opposite failure (the cover stays = white box). A failed refresh without the pencil being gone has no evidence on the tablet (a refresh fails for an INVISIBLE / detached view, which IS the collapse). The retry search runs after 30 ms and re-covers. Revisit only if a report shows `PENCIL cover hidden ... (the followed pencil is gone)` followed by `cover shown` within a second while the panel was open. |
| 5 | `findPencilFull` returned the bounds with `penNode == null` when `obtain` threw; `penWatch` then hid the cover 150 ms later (flicker). | **Fixed.** It returns null then (no cover without a node it follows). |
| 6 | `touchBack` runs the pad scan (`updateLockNumber`) after every lock-screen touch. | **Accepted.** `scheduleLockUpdate` already runs that same scan on EVERY accessibility event of the lock screen (60 ms leading edge + 120 ms trailing), so one more call 1.5 s after a touch adds nothing measurable; it is the only look that sees a pad when no event came. |
| 7 | `LOCK_TOUCH_AWAY_MS` 900 -> 1500 widens the window in which the patch is away over the stock panel. | **Accepted (deliberate).** A side-key press while the patch is merely away uses the fast path exactly as in the old 900 ms (`patchResting` stays true during a touch-away, so `fastDecline` does not refuse; the lock log writes "menu opened while the patch was away"). The longer time covers the "finger down, hesitate, then pull" pull, which the 900 ms return flashed. Unproven on the tablet: the next report's `PATCH visible again (touchBack|padBack|...)` lines decide; if they show no touchBack flash, set it back to 900. |
| 8 | `noteReturn` counted the first rest as a return; a stale `patchShowCause` could mislabel a later return. | **Fixed (stale cause).** `showWithCause()` sets the cause for ONE `patchShow` call only. The first-rest line stays (logcat only; the lock log needs a finger or pad sign < 4 s ago). |
| 9 | The dying-dialog mark is set only by the close-system-dialogs broadcast; a quick re-open without its event would be ignored for 450 ms; Back / tap-outside closes are not covered. | **Accepted.** A re-open within 450 ms of a close is physically impossible with the side key (the long-press delay is about 500 ms) and every real opening announces itself (`fastMenuOpen` clears the mark BEFORE `fastDecline`, so even a declined fast path clears it). A broader mark (every `hideOverlay`) would block the re-detect of a menu that is still open after a transient hide: a worse regression than the lingering window of a Back close, for which there is no evidence. |
| 10 | Dead parameter `foundByFullSearch`, a negation wrapper `unlockEventWasForeign`, a redundant `>= 0`. | **Fixed.** The parameter and the wrapper are gone; `foreignTreatment` keeps its `>= 0` (a clock that goes back must not count as "just after the unlock"; pinned by a test). |

Proof status: JVM tests only (`PencilRulesTest`, `HomePatchRulesTest`, `PowerMenuRuleTest`); emulator HP14 (hp) and the BN4 age check (b6) are regression guards, not proof of the tablet cases (the CI emulator has no animations, so the dying dialog cannot be reproduced there). The tablet report after a flash / a first-press leak / the white box decides.

## Change after the review (before the gate, 2026-11-09 03:40 UTC): the recheck POLLS

The first fix looked ONCE, 400 ms after the SystemUI window event. On the slow tablet the Launcher's resume after an unlock (its window gets the focus at the end of it) can take longer than that, while the keyguard's event comes at the START of the exit: one look would have kept the guard (= v0.8.12 behaviour). Now `homeForeignRecheck` looks every 400 ms until the guard's own end (`HomePatchRules.recheckAgain`), `homeFocusChanged(true)` lifts a provisional guard at once, and only a guard that ran out with the Launcher still without the focus counts as a real window. Gate runs 438-440 (head 14b4971) were cancelled for this and re-dispatched on the new head.
