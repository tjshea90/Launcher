# CD2b audit: can any part of the custom launcher make the STOCK launcher (com.android.launcher3, "Quickstep") use more RAM? (2026-11-14)

Question (Tj, 03:34Z): "Investigate all parts of the custom launcher if any function or accessibility feature could plausibly increase the ram usage of quickstep."
Method: five read-only subagents with neutral briefs, one slice each (A task / package control; B1 accessibility service lines 1-2700 + `tj_accessibility.xml`; B2 lines 2701-end + the patch / pencil / curtain / picker helpers; C system settings and configuration writes; D manifest + `launcher3/` + `wallpaperpicker/` + `phoneguide/` + `testnotifier/`). Their reports were deduplicated here. Raw reports: scratchpad only (not kept); the facts that matter are below.
Reading rules: **cannot** = the code path never reaches the stock process (system_server / SystemUI / our own process only). **could** = it makes the stock process build UI, answer node queries or receive a broadcast, and nothing is KNOWN about a leftover. **proven** = measured to raise the stock process's memory: **none is proven.**
Everything about the stock side's internals is first "from memory" in the agents' reports; the AOSP excerpts that were actually read are in `research/CD2_AOSP_Q_LAUNCHER3_FACTS_2026-11-14.md` (Android 10, plain AOSP, not MediaTek's Go build).

## Facts all five agents agree on
1. Our code **never kills, force-stops, disables, trims or removes** the stock launcher (`ShellProtocol.allowed()` denies it, `ReturnReset.shouldKill` skips it). Every effect is indirect: activity starts, accessibility actions on its windows, task-stack changes, package-changed broadcasts, global configuration changes.
2. `RouterActivity` is the ONLY HOME in both modes. The stock launcher is never the default home on Tj's tablet: it is a started HOME-type task (Quickstep session) plus the Recents host (the fallback `RecentsActivity` path of `OverviewComponentObserver`). On the friend's 48 MB tablet it is the real home. This is the one structural difference; nothing in the repo or in the AOSP excerpts says it costs memory.
3. The shell helper is usually NOT running on the tablet (report 2026-11-10: "no shell helper"), so the on-screen Recents drive (row R2) is the daily case, not the invisible task removal.
4. Naming trap: `com.android.launcher3.Launcher` inside our code is OUR class (our APK keeps the Java namespace); the stock package is matched only through `StockLauncher.find` / `stockPkg()`.
5. No tablet number for the stock process exists in any saved report (the probe lines for it, CD1c, ship with the next release; the cable dump CD1e is the deciding step).

## What the AOSP excerpts add (Android 10, plain AOSP)
- Stock Recents caches are bounded by design: 12 icons + 3 reduced-resolution thumbnails (`recentsIconCacheSize` / `recentsThumbnailCacheSize`), trimmed at `TRIM_MEMORY_RUNNING_CRITICAL`; `Launcher.onStop` trims (`TRIM_MEMORY_UI_HIDDEN`). Nothing in the read parts of the lifecycle keeps a list per session.
- Launcher is `singleTask` + `clearTaskOnLaunch` and never `finish()`es by itself; with our router as home it simply stays stopped. That explains a floor, not growth.
- Configuration changes (uiMode, font, density) are NOT handled in place: the system relaunches the activity (transient rebuild). `ConfigMonitor` reacts to font / density with an in-process grid re-init, no process kill (flag default true).
- `OverviewComponentObserver` listens for package changes of the HOME package (ours) in the fallback path, and `LauncherModel` handles package-changed for any package without checking that its model is loaded.
- NOT read (so still open): `BaseRecentsActivity` lifecycle, `Launcher.java`'s tail, MediaTek's Go changes, the Go Recents task actions.

## Ranking (reach into the stock process x frequency x plausibility; none is shown by a measurement)
1. **R2 + R1** (Recents drive + stock HOME start at every session): they make the stock process build its heaviest UI on its own, daily, every time. Emulator: flat.
2. **R8** (saver -> dark-theme flips -> Launcher / Recents relaunch): the highest-count Configuration change; the CI image could not do it any other way, so cd3n flips the saver directly.
3. **R7** (alias flips -> package-changed to the stock observer and model): never exercised by cd1 / cd2.
4. **R12 + R3** (the unfiltered accessibility subscription and the Recents watcher's tree walks): churn and heap high-water; no retention.
5. **R10** (Gboard) only as indirect system RAM pressure.

## Blind spots that no emulator run can close
Graphics / GPU memory (the CI emulator reads Graphics 0); MediaTek's Go build; days of uptime; the real wallpaper; only the tablet's `dumpsys meminfo com.android.launcher3` (CD1e) or the 3-hour average read after the A/B steps can.

## Switch-off A/B for the tablet (one change per day, read Developer options > Memory > 3 hours > Quickstep afterwards)
1. `profile_battery_saver_off` (the saver rule) OFF: removes the dark-theme flips (R8).
2. `settings_spoof` (Settings look-alike) OFF: removes the alias flips (R7).
3. `keyboard_switch` OFF: removes the IME churn (R10).
4. Accessibility service OFF for a few hours: removes R12 / R3 / R4 together (the biggest single change; most features stop).
5. `clean_start` / `return_reset` OFF: removes the on-screen Recents drive (R2); the custom launcher then keeps old cards.
