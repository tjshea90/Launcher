# CW1 audit A: SPEED (read-only; 2026-11-22; code = v0.9.17 main)

Slice: how fast the things a person feels are, and where the code is slower than it has to be. Process start and first frame, Home press / double Home / Mode flips, the profile reload and the cover that bridges it (CV1), the unlock paths, drawer / workspace load, accessibility-service cost per event, preference / settings / binder calls on the main thread, object churn.
Nothing was edited, built or run. Evidence tags: **[V]** verified by reading the code (file:line), **[I]** reasoned from the code and Android's behaviour, **[T]** only Tj's tablet can show. No tablet report of v0.9.17 exists (the newest, `research/tablet/2026-11-10-2`, is v0.9.1), so no number below measures CV1 code; the only real numbers used are from that report and are marked.
Rule of the project applied to every fix: NO loss of speed or function. "Risk" says what could break.

## 2. Findings in detail

### A1 (HIGH-MED) The cover and the unlock wait for the end of the whole load, not for what is visible
- **Where [V]:** `LoaderTask.run` (`LoaderTask.java:169-239`) does, in this order: `HomeProfile.onLoadStart` (DB switch), `loadWorkspace`, `bindWorkspace`, `waitForIdle`, `loadAllApps`, `bindAllApps`, icon-cache `updateIcons` (package-info for every launchable app), `waitForIdle`, `loadDeepShortcuts`, `bindDeepShortcuts`, `waitForIdle`, widget model `update` (every widget provider), `bindWidgets`, widget `updateIcons`, `updateHandler.finish()`, and only then `transaction.commit()` which sets `mModelLoaded`. `isModelLoaded()` is `mModelLoaded && mLoaderTask == null` (`LauncherModel.java:105-107`). `HomeProfile.ready` (`HomeProfile.java:114-124`) is exactly that plus `loaded == wanted`. `waitForIdle` waits for the MAIN looper to go idle, in 1 s slices, until it does (`LoaderTask.java:132-135`, `BaseLoaderResults.java:302-309`), so each of the three waits lasts as long as the main thread keeps binding or animating.
- **What waits for it [V]:** `waitForProfile` (cover, cap 3.5 s, `TjAccessibilityService.java:2372-2396`: after a handshake unlock and from `profileCover` on a visible flip) and `settleHome` (cap `SETTLE_PROFILE_CAP_MS` 4.5 s, `:2416`: the custom-home return).
- **Why it matters:** what the person sees is the bound workspace (step 1) and, when the drawer is opened, the all-apps list (step 2.2). Steps 2.3 to 5 (icon cache refresh, deep shortcuts, widgets) are invisible work, yet the cover stays up for them. On a Go tablet with little RAM these steps run on top of the main thread's own binding.
- **Before CV1 / after [V from the tablet report v0.9.1]:** "custom home in front +169 ms after the clean-up" (`research/tablet/2026-11-10-2`, line 739). When the clean-up has something to do (Recents clear about 0.9 s) the reload runs in parallel and may be hidden inside that time. When there is NOTHING to clear (`ReturnReset.java:221-226` goes straight to `settleHome`) or on a plain double Home, the whole load is now added: [I] 0.2-1.5 s, [T].
- **Fix:** two signals instead of one. (1) A new `HomeProfile.appsBound(profile)` set from `LoaderTask` right after `mResults.bindAllApps()` (line 194; after `verifyNotStopped()`, so a cancelled run never sets it) and cleared by `onLoadStart`. `ready` for the COVER and the unlock becomes `loaded == wanted && appsBound`. (2) Keep `isModelLoaded()` as the stricter "fully loaded" fact for anything that needs it (reports, the icon-update users). Cost saved: steps 2.3, 3, 4, 5 and the second and third idle waits.
- **Risk MED:** the drawer and the workspace must show the new profile's data when the cover goes. After `bindAllApps` the apps list is the new one (the filter follows the live mode already); deep-shortcut and widget lists are only needed when their screens open. The AllAppsStore defers updates until the next draw (`Launcher.executeOnNextDraw`, `Launcher.java:2273-2285`): check that "bound" means "visible" with the emulator section that opens the drawer right after a flip (`ul`). Do NOT do this without the tablet number first: the lock log already prints `PROFILE profile ready +N ms` (`TjAccessibilityService.java:2389`) and `HOME custom home in front +N ms` (`:2421`); the next tablet report of v0.9.17 says how big A1 really is.
- **Related, not changed:** every flip is a full `forceReload` (`LauncherModel.java:318-334`). Both layout databases stay open and the switch is a pointer swap (`LauncherProvider.java:181-198`, helpers kept in `mProfileHelpers`), so there is no database re-open cost on a flip after the first. Keeping two bound models would double RAM (slice C) and is not recommended.

### A2 (MED) `Mode.set` is a long synchronous chain, and double Home runs it before starting the Launcher
- **Where [V]:** `RouterActivity.java:69-73` calls `Mode.set(this, CUSTOM)` and only at line 81 `startOurs`. `Mode.set` (`Mode.java:94-117`): `commit()` (fsync of the mode file, line 104), `AnimationSpeedup.syncNow` (a `static synchronized` method that also runs on worker ticks, so the main thread can wait on the monitor; it does the notification-quiet, radio-icon, VPN and animation-scale rules with binder and settings calls, `AnimationSpeedup.java:150-261`), `SettingsSpoof.syncSoon`, `HomeProfile.syncNow`, `BatterySaverGuard`, `StockForceStop` / `StockRefresh` (thread start), `AppOrigin`, `TaskOrigin`, then `KeyboardSwitch.apply` (input-method list over binder, a secure-settings read and write, a preference commit), `TileProfile.apply`, `ImmersiveProfile.apply`, `BatterySaverGuard.check`.
- **Why it matters:** Router, Launcher and the accessibility service share one main thread. The Launcher's `onNewIntent` / resume is queued behind all of this. It is the same chain after a handshake (`TjAccessibilityService.java:1994`) and a plain unlock (`:2015`).
- **Cost:** [V] order and content; [I] fsync 3-15 ms, input-method list 5-30 ms when the keyboard switch is active, settings writes 1-5 ms each; [T] total.
- **Fix:** keep the part that the NEXT step reads (the mode value itself, `HomeProfile.syncNow`, `AnimationSpeedup` start/stop) synchronous. Move the rest (`KeyboardSwitch`, `TileProfile`, `ImmersiveProfile`, `BatterySaverGuard`, `StockForceStop` / `StockRefresh` notes, `TaskOrigin`, `AppOrigin`) to ONE serial background executor in the same order (a `Mode.afterSet` queue). In `RouterActivity` start our Launcher first and run the rest after `startActivity` returns (the fan-out only needs to have happened "soon", not before the Launcher starts; the Launcher's resume is level-triggered on the mode).
- **Risk LOW-MED:** (a) order of the side effects among themselves must stay (one serial queue keeps it); (b) the unlock paths want the keyboard / tile profile to be right before the first thing the person does: check `KeyboardSwitch` and `TileProfile` have no reader on the same thread right after `set` (grep their callers); (c) JVM test for the queue order with a fake executor; emulator section `x` and `legacy` run the real `apply`.

### A3 (MED) The return clean-up does its planning on the caller's thread
- **Where [V]:** `ReturnReset.run` (`ReturnReset.java:195-238`) runs on the thread that calls it: `RouterActivity.java:110` (main) and `TjAccessibilityService.java:2017` (main). Before the worker thread exists it calls `invisibleTargets` (`:99-118`: `StockLauncher.find` = package-manager query, `Settings.Secure` read, and when nothing is tracked yet a `queryIntentActivities` over ALL launchable apps), `guard` (`:124-131`: a second `StockLauncher.find` and a second settings read), `AppOrigin.tracked/pending/custom` (each copies a stored string set), and in the no-helper branch `clearNotifications`, `clearRecents`, `svc.hasNotificationIcons()` (an accessibility window scan), `NotifSightings.dirty`, `recentsNeeded`, `labelsOf` (label lookups per package) and a `LockLog` plan line (`:205-220`).
- **Why it matters:** it runs right after `startActivity` of the Launcher, on the thread that has to draw it. On Tj's tablet the shell helper is usually not alive (HLP1), so the no-helper branch is the normal one.
- **Cost:** [V] on the caller; [I] 30-150 ms; [T].
- **Fix:** post the planning (`invisibleTargets`, `guard`, the app-list query, `labelsOf`) to the existing worker or a new `HandlerThread`, and hop back to main only for the window actions (the cover, the shade step, Recents). Cache the settings-derived input-method package for the length of one run.
- **Risk LOW:** the decisions must use the same inputs (the worker reads the same preferences). Keep `showResetCover` first on main (it must be up before the clean-up starts), the planning behind it.

### A4 (MED) `settleHome` polls the accessibility tree every 40 ms before it looks at the cheap fact
- **Where [V]:** `TjAccessibilityService.java:2411-2432`: each tick calls `isForeground(getPackageName())` (`:2414`, `getRootInActiveWindow()` at `:4313`) FIRST, and only then, `if (front && Unified.active && !HomeProfile.ready ...)` (`:2416`), reposts 40 ms later. The Launcher binds on this same main thread while the cover waits (A1), and a root fetch of our own window is a binder round trip that the service answers on the main thread (prefetch of up to 50 nodes).
- **Cost:** [I] 2-10 ms per tick, 25-100 ticks when the load is slow, i.e. up to a few hundred ms of main-thread time in the middle of the bind. [T].
- **Fix:** order the test: first `Unified.active && !HomeProfile.ready && dt < cap` AND `TjHooks.launcherInFront()` (a volatile flag) then repost at 40-60 ms without any tree fetch; fetch the root ONCE when the model is ready (or when `dt >= 200` for the `goHome` press branch). Same for `waitForProfile` (it already polls cheap facts, only `isForeground(resumedPkg)` once).
- **Risk LOW:** `isForeground` is the truth for "our window is in front"; `TjHooks.launcherInFront()` is the resumed flag (used in the handshake check next to it, review CV1-5). Keep the final `isForeground` call before the cover is removed.

### A5 (MED) Plain PIN after a Quickstep session starts the reload late
- **Facts [V]:** the tablet report v0.9.1 shows "UNLOCK plain -> custom (a Quickstep session ended), Enter to unlock 1174 ms" (line 735), other unlocks 894-1397 ms (lines 731, 750, 762, 780, 811 of `research/tablet/2026-11-09` and `2026-11-10-2`). So the PIN is submitted about 0.9-1.4 s before `applyUnlockChoiceBody` runs. In that run the custom-profile flip starts at `Mode.set(CUSTOM)` (`TjAccessibilityService.java:2015`), i.e. after that second.
- **Handshake case is fine [V]:** the unlocked-profile reload starts when the handshake is accepted (`secretAccepted`, `:1798-1808`), long before Enter.
- **Idea:** when Enter is pressed on the PIN pad and no handshake matched, the unlock will be plain (if the PIN is right). Start the custom-profile reload at that moment instead of at USER_PRESENT, using the second the keyguard needs anyway. Gain = min(Enter-to-unlock, reload duration), up to about 1 s; with A1 done the reload may already be hidden by the clean-up, so this one is worth it only if the tablet number says the cover still outlasts the clean-up.
- **Why it is not trivial:** `HomeProfile.wantedProfile` is a pure function of the mode; a reload to the custom profile while the mode still says QUICKSTEP would be undone by the next level-triggered `syncNow` (resume, `Mode.set`). It needs a "provisional wanted profile" with an expiry, cleared on a wrong PIN, a screen-off or a handshake. A wrong PIN costs a reload back.
- **Risk MED-HIGH** (lock-safety rule of the project: never locked out, never a crash loop). Do NOT build before the tablet shows `PROFILE profile ready +N ms` after a plain unlock larger than the clean-up time.

### A6 (MED-LOW) Handshake front check does work it throws away
- **Where [V]:** `TjAccessibilityService.java:1996-1998`: `StockLauncher.find(this)` (uncached query), `isForeground(resumedPkg)` (only if a remembered app exists), then in the argument list `stock != null && isForeground(stock...)` AND `isForeground(getPackageName()) && TjHooks.launcherInFront()` are both evaluated before `UnifiedRules.quickstepFrontOk` picks one (`UnifiedRules.java:59-61`: `active ? ownInFront : stockInFront`). With the unified launcher active the stock answer is never used, yet its root fetch and the package query run. `verifyQuickstepFront` (`:2071`) has the same eager `isForeground(target)`.
- **Cost:** [I] one package query (3-15 ms) plus up to three root fetches (2-10 ms each) on the unlock path, on the thread that draws the first frame. [T].
- **Fix:** evaluate lazily: `active ? own : stock`; take the active window's package ONCE (`getRootInActiveWindow()` once, compare three names) and use `stockCached()` (`:3137-3141`) for the stock name.
- **Risk LOW:** pure re-ordering; `UnifiedRules.quickstepFrontOk` keeps its signature (add a JVM test on the lazy form).

### A7 (LOW-MED) Extra fsync commits on the unlock path
- **Where [V]:** `Mode.set` commit (`Mode.java:104`), `Mode.confirmQuickstep` commit (`:42`) called at `TjAccessibilityService.java:1806` (secret accepted) and again at `:2002` (unlock), all on the main thread, all rewriting the same `tj_mode` file and syncing it. `markFailOpen` (`:49`) also commits (rare).
- **Cost:** [I] 2-15 ms each on eMMC. The one at `:2002` is on the first-frame path of every handshake unlock.
- **Fix:** write `qsConfirmedAt` in the same editor as the mode in the handshake case (`Mode.setConfirmed`), and make the second stamp `apply()`: the router and the service live in the same process, so they read the in-memory value at once; only a process kill in the few ms before the write lands would lose it, and the cost of that is the old safety net ending one Quickstep session early.
- **Risk LOW** (JVM test of the pair; the emulator unlock sections prove the safety net still holds: `ac`).

### A8 (LOW) The unlocked-profile home runs the custom patch machinery
- **Where [V]:** the Launcher's draw listener calls `homeDrew()` on EVERY draw (`TjHooks.java:68-73`); `homeDrew` -> `scheduleCurtain` (a posted look per quiet burst; `buildCurtainNow` then spends about eight preference reads and two or three binder calls to answer "not custom", `:2202-2221`), and every 2 s of drawing `refreshLayersSoon` while no patch window exists (`:1013-1017`). `refreshLayers` -> `patchTarget` asks `keyguardLocked()` (a fresh binder call, `:1266`), `homePatchTarget` (`homeFacts`, many reads, `:729-744`), later `keyguardLocked()` again (`:1465`). Triggers: every state transition start and end (`TjHooks.setNormal`, `:193-196`), every resume (`:99`), every wallpaper step change (`:654-662`), the `mode` preference change (`:593`).
- **Cost:** [I] 0.3-1 ms per layer refresh; per burst a handful; negligible for speed, small for battery (slice C).
- **Fix:** one gate at the top of `homeDrew` / `scheduleCurtain` / `refreshLayers`: when the mode is Quickstep, the keyguard is not up (`keyguardLockedFast`), and no patch window exists, return at once. The first `refreshLayers` after the flip still tears an old patch down.
- **Risk MED:** the LOCK patch works in every mode ("AD7a: any lock screen, whatever the mode flag says", `:1268`), so the gate must be "Quickstep AND not locked". Cover with a JVM rule (`HomePatchRules`-style pure function) and the emulator sections `hp` / `pt` solo.

### A9 (LOW) `StockLauncher.find` is uncached on hot paths
- **Where [V]:** `StockLauncher.java:30-32` (`queryIntentActivities`, MATCH_DEFAULT_ONLY). Call sites: `TjAccessibilityService.java:1996`, `ReturnReset.java:100, 125, 277`, `AppOrigin.java:72, 104`, `RouterActivity.java:122`, `WallpaperPickerChoice.java:102, 158`. The service has `stockCached()` (60 s, `:3137-3141`), used once.
- **Fix:** move the 60 s cache into `StockLauncher` itself (invalidate on package change broadcast already handled elsewhere, or after 60 s) and use it everywhere except `startStock` (the emergency exit may ask fresh).
- **Risk LOW:** a stock launcher replaced inside 60 s is a corner; the emergency exit keeps the fresh query.

### A10 (LOW) Uncached preference handles on per-app paths
- **Where [V]:** `HiddenApps.p` (`HiddenApps.java:22`) and `CrashGuard.wasTripped` / `isPaused` / `automationOff` (`CrashGuard.java:71, 88, 93`) call `getSharedPreferences` on every call (the `ContextImpl` lookup takes a global lock). `HiddenApps.isShown` / `isPackageShown` (`:74-98`) run per app at every load and call `Unified.unlockedHome` (mode, feature, debuggable, `wasTripped`) and `SettingsSpoof.hidesRealSettings`. `Features` and `Mode` already cache their handles.
- **Cost:** [I] about 500 lookups per load, 1-3 ms in total. Small.
- **Fix:** cache the handle in a static (as `Features.p` does) and read `Unified.unlockedHome` once per load pass. Only worth it if the files are open anyway.
- **Risk LOW** (the "Clear data" case: handles are rebuilt with the process).

### A11 (LOW) Fixed per-Home-press cost
- **[V]:** `RouterActivity.route` runs `ProfileSession.checkBoot` (a settings read), `KeepAliveService.ensure`, `LockLog.add` (queued), and in a Quickstep session `UsageGap.sessionEndedWhileAway` (`UsageGap.java:61-79`: two binder calls plus a usage-events query, incremental). In the unified world every Quickstep Home press pays it before our Launcher starts (it has to: its answer can flip the mode and so the profile).
- **Cost:** [I] 1-5 ms, bounded by the incremental window (`:72-76`). No fix needed; listed so nobody re-audits it.

### A12 (LOW, other slices) Sleeper threads and a binder per mode change
- **[V]:** `StockForceStop.afterQuickstepSession` and `StockRefresh.afterQuickstepSession` each start a thread that sleeps about 45 s per Quickstep session end (`Mode.java:109-110`); `updateKeyFilter` (`TjAccessibilityService.java:1765-1780`) calls `getServiceInfo` (binder) per call. They belong to slice C (RAM / CPU) and D (the stock launcher's sleep); one scheduled handler task would replace the threads.

## 3. Checked and fine (no finding)
- `TjApplication.onCreate` 48 ms on the tablet [V from report v0.9.1]; the Router is `Theme.NoDisplay`, `singleInstance`, finishes at once; `Features` and `Mode` cache their preference handles; `LockLog.add` is queued (no disk write on the unlock path); `Mode.recordHomePress` / `lastHomePressMs` are memory only.
- `HomeProfile.syncNow` is cheap when nothing is to do (two memory reads and the mode), spacing-guarded (1.5 s) and retried by a handler; `HomeProfile.onLoadStart` is one `ContentResolver.call` into the same process.
- The two layout databases both stay open (`LauncherProvider.mProfileHelpers`): a flip never re-opens a database; `seedFromCustom` runs once, in one transaction, on the model thread.
- `HiddenApps.reloadLauncher` uses `LauncherAppState.getInstance`, which could construct the app state on a caller's thread, but `HomeProfile.syncNow` only reaches it when `loaded != null`, i.e. after a load (so the state exists).
- `TjHooks.onLauncherResumed`: `RecentsGuard.excludeOurTasks` is once per Launcher instance (W2); the stray-custom guard is skipped in the unified world (`UnifiedRules.strayCustomApplies`).
- E3 / E4 / E5, S12, U1, M1, M2, M9, M10 (CG1B / PERF_AUDIT items) are in the code (checked at `evaluateScan`, `Features.setStringAsyncIfChanged`, `allowedReadOnly`, `RecentsGuard`).
- The service's per-event entry (`onAccessibilityEvent`, `:67-106`) filters early; `keyguardLockedFast` caches 250 ms; `homeCropValid` caches its answer.
